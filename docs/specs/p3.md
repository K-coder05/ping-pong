# Spec: P3 Phone Input

Nov 19, 2026 · @Khiem · revised Nov 23, 2026 after a design review

## How to use this spec

This spec covers seven seams that let a player use their Phone as an Input: the Phone's motion sensors stream to the laptop over a peer-to-peer WebRTC connection, and a new Phone Input turns that stream into Swings with a Face Angle. Each seam is one Claude Code session and one pull request. Start each session with:

```
Read docs/specs/p3.md, GLOSSARY.md, docs/adr/ and CLAUDE.md. Implement seam <ID> only.
First propose a plan that lists every file you will create or change,
maps it to the seam's Owns list, and names the tests you will write.
Wait for my OK before writing code.
```

**Order**: P3-0 → P3-a, P3-b and P3-f in parallel (separate git worktrees) → P3-c and P3-d in parallel → P3-e.

## Project context

**Already built** (S0, P1 and P2 are merged; see `docs/specs/s0-p1.md` and `docs/specs/p2.md`): Return Drill and Match, played with the Camera Input (MediaPipe pose, a Swing detector in shoulder widths/s) or the developer mouse (`?input=mouse`). The input contract is in `src/input/types.ts` (`SwingEvent { t, peakSpeed, side, vertPath }`, `SwingSource`) and `src/input/handPosition.ts` (`HandPosition { t, u, py }`, `HandPositionSource`). Also built: onboarding with handedness and Timing calibration, the start screen, the Detection test (`detection.html`), the latency harness (`latency.html`), the play log and the balance harness. All randomness comes from `makeRng(seed)`. There is no `src/contracts/` folder and no recorder; P3-0 adds what this stage needs.

**Why**: Swings should register more reliably and sooner with the Phone than with the Camera. Spin from the Face Angle is a bonus. The stage passes when, on the same laptop and player:

1. the Detection test detects more Swings with the Phone than with the Camera,
2. the Detection test's idle phase has fewer false triggers with the Phone, and
3. the flash test (P3-d) shows the Phone's Swing Onset arriving sooner than the Camera's.

**Words**: use `GLOSSARY.md` everywhere, in code, comments, tests and UI text. The new terms are **Input** (Camera or Phone), **Phone**, **Zeroing** and **Face Angle**. The **Paddle** is only the on-screen bat: never call the Phone a paddle or a controller. In code, the Face Angle is `faceAngle`, not `tilt`, and the Phone's page is `phone.html`.

**Decisions to respect**:

- ADR 0001: Returns come from Swing timing, never Paddle–ball contact. The Phone adds fields to the same resolver. Timing still picks a Return's direction, so `SwingEvent` gets no `horizDir`.
- ADR 0003: Spin control depends on the Input: Lift with the Camera, Face Angle with the Phone.
- ADR 0004: pairing goes through our own Node signaling server on Render's free tier, with relay, not TURN, as the fallback.

**How it fits together**

1. The player picks Phone on the start screen. The laptop asks the signaling server for a room and shows a QR code for `https://<pages-host>/ping-pong/phone.html?room=<code>`, plus the room code in large text.
2. The Phone scans it, opens `phone.html` and joins the room over the signaling WebSocket. Opened without `?room`, the page shows a box for typing the code by hand.
3. The two pages exchange the WebRTC offer, answer and ICE candidates through the server, then talk directly over data channels. The server is no longer in the path.
4. The Phone sends one motion packet per sensor event. The laptop's Phone Input turns packets into `SwingEvent`s carrying a `faceAngle`, plus a live Paddle position.

**Hosting** (ADR 0004): `server/signal.ts` (Node + `ws`) runs on Render's free tier. The game reads its URL at build time from `VITE_SIGNAL_URL` and sends it a wake-up request (`GET /health`) as soon as the game page loads, because the free tier sleeps after about 15 minutes idle. In dev the server runs behind Vite's `/signal` proxy.

**Dev setup (HTTPS on your LAN)**: browsers only expose motion sensors and the camera on secure pages, so the Phone must load the dev build over HTTPS.

- Vite with `server.host: true` and a self-signed certificate plugin (`@vitejs/plugin-basic-ssl`). Open `https://<laptop-LAN-IP>:5173/phone.html` on the Phone and accept the certificate warning once.
- Run the signaling server behind Vite's dev proxy (`/signal`, WebSocket enabled), so the Phone connects over the same HTTPS origin. A secure page can't open a plain `ws://` socket.
- Keep the laptop and Phone on the same Wi-Fi network. Some campus and guest networks block device-to-device traffic; P3-e's relay fallback covers that.

**Rules for every session**

1. Change only files in the seam's Owns list, plus the tests next to them. If something else must change, stop and ask.
2. Don't add dependencies unless the seam names them.
3. Keep the motion-to-Swing logic pure and tested with recorded Phone log fixtures. Keep WebRTC, sensors and the DOM in thin wrappers.
4. Inject time as a `now: () => number` function and randomness as an `Rng` from `makeRng`, as the existing code does. Don't add new `Clock` or `Rng` interfaces.
5. Before saying done, run `npm test` and `npm run typecheck`, and list anything you couldn't verify yourself (anything that needs a real Phone).

**Numbers in this spec**: thresholds, rates and spin mappings are starting guesses to tune with real Phones, not measured values.

## P3-0 Input contract and Phone log

**Goal**: the foundation the other seams build on. It extends the existing input contract, defines the Phone's packet and link types, adds a Phone log for recording fixtures, and gives `phone.html` its build entry.

**Owns**: `src/input/types.ts`, `src/input/handPosition.ts`, `src/phone/types.ts` (new), `src/phone/phoneLog.ts` and test, `phone.html` (a placeholder only; P3-b replaces it), `vite.config.ts` (only the `phone` build entry).

**Depends on**: nothing in P3. **New dependencies**: none.

**Contract changes** (additive; existing callers compile unchanged)

```ts
// src/input/types.ts
interface SwingEvent {
  // ...existing fields...
  /** Face Angle at Swing Onset, radians from Zero; + = closed (toward the floor), − = open. Only the Phone sets it. */
  faceAngle?: number;
}

// src/input/handPosition.ts
interface HandPosition {
  // ...existing fields...
  /** Face Angle now, radians, for drawing the Paddle tipped. Only the Phone sets it. */
  faceAngle?: number;
}
```

A Swing that carries a `faceAngle` is resolved with the Face Angle rules (P3-f). There is no `source` field.

**Phone types** (`src/phone/types.ts`)

```ts
export interface MotionPacket {
  seq: number;                        // increments per packet
  tPhone: number;                     // ms, the Phone's performance.now()
  rot: [number, number, number];      // rotationRate alpha, beta, gamma, deg/s
  acc: [number, number, number];      // accelerationIncludingGravity x, y, z, m/s²
  ori: [number, number, number];      // deviceorientation alpha, beta, gamma, deg
}
export type ControlMessage =
  | { type: 'ping'; t0: number }
  | { type: 'pong'; t0: number; t1: number; t2: number }
  | { type: 'zero' }
  | { type: 'haptic'; ms: number };
export type LinkStatus = 'idle' | 'waiting' | 'connecting' | 'connected' | 'relay' | 'disconnected';
export interface PhoneLink {
  status(): LinkStatus;
  onStatus(cb: (s: LinkStatus) => void): () => void;
  onPacket(cb: (p: MotionPacket, tRecv: number) => void): () => void;
  onControl(cb: (m: ControlMessage, tRecv: number) => void): () => void;
  sendPacket(p: MotionPacket): void;   // Phone side
  sendControl(m: ControlMessage): void;
  close(): void;
}
```

**Phone log** (`src/phone/phoneLog.ts`): the laptop records what it receives as JSONL, one object per line:

- `{ "type": "packet", "tRecv": number, ...MotionPacket }`
- `{ "type": "zero", "tRecv": number }`

It exposes a recorder (`record(packet, tRecv)`, `zero(tRecv)`, `toJsonl()`) and `parsePhoneLog(text)` for tests. Fixtures are labelled by file name (`fixtures/phone/phone-fore-top-03.jsonl`). Phone logs are replayed only in tests, through the Swing detector; there is no in-game replay.

## P3-a Pairing and signaling

**Goal**: pair a Phone with the laptop by scanning a QR code, then connect them peer to peer with WebRTC: a fast, lossy channel for motion and a reliable one for control messages. Deploy the signaling server.

**Owns**: `server/signal.ts` and test, `src/phone/link.ts`, `src/phone/packet.ts` (`encodePacket`/`decodePacket`) and test, `src/phone/pairing.ts` (laptop: create a room, draw the QR code and room code), `src/phone/signalUrl.ts` (`VITE_SIGNAL_URL` and the wake-up request), `vite.config.ts` (HTTPS plugin and `/signal` proxy; not the `phone` entry), `package.json` (a `signal` script and the dependencies below), `render.yaml`, `.github/workflows/deploy.yml` (only to pass `VITE_SIGNAL_URL` to the build), `e2e/pairing.spec.ts`.

**Depends on**: P3-0. **New dependencies allowed**: `ws`, `qrcode`, `@vitejs/plugin-basic-ssl`, and `@playwright/test` (dev only).

**Packets** (`src/phone/packet.ts`): `encodePacket(p: MotionPacket): ArrayBuffer` (binary, fixed size) and `decodePacket(b: ArrayBuffer): MotionPacket`.

**Signaling server** (`server/signal.ts`, Node + `ws`)

- Messages are JSON: `create` → `{ room }`; `join { room }`; `signal { data }` is forwarded to the other peer in the room.
- Room codes: 5 characters from an alphabet without look-alikes (no 0/O, 1/I/L). At most 2 peers per room. Rooms expire after 10 minutes idle.
- `GET /health` answers 200, for the wake-up request and Render's health check.
- The server never sees motion data (until P3-e's relay).

**WebRTC link** (`src/phone/link.ts`, used by both pages)

- Two data channels: `motion` with `ordered: false, maxRetransmits: 0` (a late packet is useless, so never wait for it) and `control`, reliable and ordered.
- ICE servers are configurable and empty by default, since same-network host candidates are enough. No TURN (ADR 0004).
- Status changes drive the pairing UI: waiting for Phone, connecting, connected, disconnected.

- [ ] `encodePacket`/`decodePacket` round-trip tests, including negative and large values
- [ ] Server tests: create and join, a third peer is rejected, a bad room code fails cleanly, rooms expire, `/health` answers
- [ ] Playwright test: two browser pages on localhost pair through the server and pass 1,000 motion packets with fewer than 1% lost, plus 10 control messages with none lost

## P3-b Phone page

**Goal**: the page the Phone opens from the QR code. It asks for motion-sensor permission, streams one packet per sensor event as fast as the Phone produces them, keeps the screen awake, and handles Zeroing and haptics.

**Owns**: `phone.html`, `src/phone/phonePage.ts`, `src/phone/sensors.ts` and test, `src/phone/phonePage.css`.

**Depends on**: P3-0. Runs in parallel with P3-a and P3-f. Don't edit `vite.config.ts`; P3-0 already added the entry.

**Contract**

```ts
export interface SensorSource {
  start(): Promise<'granted' | 'denied' | 'unsupported'>;   // call from a tap handler
  onPacket(cb: (p: MotionPacket) => void): () => void;
  rateHz(): number;                                          // measured over the last second
  stop(): void;
}
export function createSensorSource(win: Window, now: () => number): SensorSource;
```

**Behaviour**

1. **Room code**: with `?room=<code>`, join that room. Without it, show a box for typing the code by hand.
2. **Start button**: a large "Tap to start" button. Inside its tap handler, if `DeviceMotionEvent.requestPermission` exists (iOS), call it and `DeviceOrientationEvent.requestPermission`; iOS only allows this from a user gesture. On denial, show how to re-enable motion access in the browser settings.
3. **Streaming**: listen to `devicemotion` and `deviceorientation`. Cache the latest orientation. On every `devicemotion` event, build a packet (`rotationRate`, `accelerationIncludingGravity`, the cached orientation, `seq`, `tPhone`) and send it immediately. No batching, no timers.
4. **Screen awake**: request a screen wake lock where supported, and re-acquire it when the page becomes visible again.
5. **Zeroing**: show "Hold the phone like the handle of a bat, screen facing your palm side, point it at the screen and tap Zero". Tapping Zero sends `{ type: 'zero' }`. The Zero button stays available, so the player can Zero again at any time; the laptop decides when to apply it (P3-c, P3-e).
6. **Haptics**: on a `haptic` control message, call `navigator.vibrate(ms)` where the browser supports it. Android Chrome does; iOS Safari doesn't, so skip silently.
7. **UI**: connection status, the live sample rate, a full-screen tap area that blocks scrolling and pinch zoom, and a reminder to grip firmly.

- [ ] `sensors.ts` tests with synthetic `devicemotion`/`deviceorientation` events: packets carry the right fields, `seq` increments, `rateHz` is correct for a simulated 60 Hz stream
- [ ] Permission flow tests with a mocked `requestPermission`: granted, denied, and unsupported (Android, where no prompt is needed)
- [ ] `npm run build` outputs the real `phone.html`

## P3-f Face Angle in the resolver

**Goal**: Swings that carry a Face Angle set Spin and answer an incoming Shot's Spin by Face Angle instead of Lift (ADR 0003), for Returns and the player's Serves. Camera Swings are unchanged.

**Owns**: `src/game/faceAngle.ts` and test, `src/game/shotResolver.ts` and test, `src/game/constants.ts` (knobs `FACE_ANGLE_DEAD_DEG`, `FACE_ANGLE_FULL_DEG`, `RETURN_BACKSPIN_MAX_REVS`, `PHONE_SPEED_FULL`), `src/tools/simPlayer.ts` and test, `scripts/balance.ts`, `docs/balance-report.md`.

**Depends on**: P3-0. Runs in parallel with P3-a and P3-b; it needs no Phone, only `SwingEvent.faceAngle`.

**Face Angle share** (`src/game/faceAngle.ts`): `faceAngleShare(faceAngleRad, params)` returns f in [−1, 1]: 0 within ±`FACE_ANGLE_DEAD_DEG` (10°), rising linearly to ±1 at `FACE_ANGLE_FULL_DEG` (45°), positive when closed.

**Spin set by the Face Angle**

| Face Angle at Swing Onset (vs Zero) | Spin on the Return or Serve |
| --- | --- |
| Upright, within ±10° | None |
| Closed (toward the floor) | Topspin, up to `RETURN_TOPSPIN_MAX_REVS` at 45° |
| Open (toward the ceiling) | Backspin, up to `RETURN_BACKSPIN_MAX_REVS` at 45° |

The amount scales with the speed factor `min(1, peakSpeed / PHONE_SPEED_FULL)`, where `PHONE_SPEED_FULL` is 7.5 (900 deg/s at P3-c's `dpsPerUnit` of 120). Lift is ignored, and there is never any Sidespin.

**Answering Spin with the Face Angle** (ADR 0001: only the target moves). With f the Face Angle share and s the incoming Topspin share (negative for Backspin), as in `answerSpin`:

- Against Backspin (s < 0), depth shrinks by `SPIN_ANSWER_M × max(0, f − s)`, with the same `RETURN_MIN_DEPTH_M` floor as today.
- Against Topspin (s > 0), depth grows by `SPIN_ANSWER_M × max(0, s − f)`.

A flat face is punished by both spins, unlike the Camera's flat Swing (ADR 0003).

**Balance**: add a Phone player model to the balance harness. Its Face Angle matches the incoming Spin with Gaussian error (starting guess σ = 15°), and the rest is as the fitted Camera model. Report the Phone model against the Camera model at each Difficulty in `docs/balance-report.md`.

**Done (Claude checks)**

- [ ] Existing resolver tests pass unchanged: Swings without `faceAngle` behave exactly as before
- [ ] `faceAngleShare` tests: dead zone, saturation at 45°, sign
- [ ] Resolver tests: Topspin for closed and Backspin for open, speed scaling, no Sidespin, Lift ignored, the same rules on Serves
- [ ] Answer tests: matching the Spin moves nothing; a flat face goes short against Backspin and long against Topspin; the depth floor still holds
- [ ] Balance report compares the Phone and Camera models per Difficulty

**Out of scope**: producing `faceAngle` from real packets (P3-c).

## P3-c Phone Input

**Goal**: a Phone Input that turns motion packets into `SwingEvent`s with a Face Angle, plus a live Paddle position, so the game can't tell it apart from the Camera except through `faceAngle`.

**Owns**: `src/input/phoneInput.ts`, `src/input/phoneSwing.ts` (pure detector) and test, `src/render/paddle.ts` (tip the Paddle by `faceAngle`), `src/render/debugMode.ts` or `src/render/debugPanel.ts` (a Phone log download button), `src/input/mouseInput.ts` (only `swingInputMode`, to accept `phone`), `src/main.ts` (only to wire the developer flag `?input=phone`, with pairing from `src/phone/pairing.ts`), `fixtures/phone/*.jsonl`.

**Depends on**: P3-a, P3-b. Runs in parallel with P3-d.

**Contract**

```ts
export interface ClockOffset { toLocal(tPhone: number): number }   // P3-d provides the accurate one
export function naiveOffset(): ClockOffset & { observe(tPhone: number, tRecv: number): void };
// naive: offset = min over the last 2 s of (tRecv - tPhone)

export interface PhoneSwingParams { onDps: number; offDps: number; cooldownMs: number; dpsPerUnit: number }
// starting guesses: 400, 150, 400, 120
export class PhoneSwingDetector {
  constructor(p: PhoneSwingParams, hand: 'right' | 'left');
  zero(neutral: MotionPacket): void;
  push(p: MotionPacket, tLocal: number): SwingEvent | null;
}
export function createPhoneInput(link: PhoneLink, now: () => number, offset: ClockOffset, hand: () => 'right' | 'left'): SwingSource & HandPositionSource;
```

**Swing detection** (the Phone's gyro plays the role of the Wii Remote's accelerometer)

1. Angular speed is the magnitude of `rot`, in deg/s.
2. **Swing Onset**: above `onDps` for 2 consecutive packets, outside the cooldown. **Re-arm**: when it drops below `offDps`.
3. `peakSpeed` is the peak angular speed over the onset packets divided by `dpsPerUnit`, so Phone Swings land on the same scale as Camera Swings (400 deg/s ≈ 3.3, near the Camera's onset threshold).
4. **Forehand or Backhand**: from which way the Phone rotates (the sign of the dominant rotation axis at Onset) relative to the hitting hand. Learn the sign convention from fixtures, not by assumption.
5. `faceAngle`: the bat face's angle from Zero at Onset, from orientation; positive when closed. Learn the axis from fixtures.
6. `vertPath` is 0. The Phone doesn't use Lift (ADR 0003).

**Zeroing**: on a `zero` control message, the next packet's orientation becomes neutral. Before the first Zeroing, the Phone Input emits no Swings. (P3-e defers a Zeroing that arrives mid-Rally.)

**Paddle position**: the Phone gives no position, so `latest` is a fixed hitting point (`u` = 1, `py` = 0, starting guesses) shifted sideways by yaw from Zero (±1 shoulder width at ±45°), with `faceAngle` from orientation. Good enough to draw.

**Fixtures you record mid-session**: Claude's first step adds the Phone log download to debug mode; pause the session there and record these. At least 10 each of `phone-fore-top-*`, `phone-fore-flat-*` and `phone-fore-chop-*`, the same three for backhand, and 2 minutes of `phone-idle-*` (walking, adjusting grip). Each clip starts with a Zeroing.

- [ ] Face Angle sign matches the label (closed on top, open on chop) on at least 90% of top and chop clips

## P3-d Clock sync and latency

**Goal**: put Phone timestamps on the laptop's clock accurately enough for the Hit Window, then measure whether the Phone beats the Camera. Those measurements are the stage's done test.

**Owns**: `src/phone/clock.ts` and test, `src/phone/latencyOverlay.ts`, `src/tools/latencyHarness.ts` (a `?flash` mode), `src/tools/detectionTest.ts` (`?input=phone`), `src/phone/phonePage.ts` (only to answer pings).

**Depends on**: P3-a, P3-b. Runs in parallel with P3-c. P3-c switches from `naiveOffset` to `ClockSync` once both merge.

**Contract**

```ts
export class ClockSync implements ClockOffset {
  constructor(link: PhoneLink, now: () => number, opts?: { samples: number; resyncMs: number }); // 20, 10000
  start(): void; stop(): void;
  offsetMs(): number;     // Phone minus laptop
  rttMs(): number;        // median of the kept samples
  toLocal(tPhone: number): number;
}
export interface LinkStats { oneWayP50: number; oneWayP95: number; lossPct: number; rateHz: number }
export function linkStats(window: { tPhone: number; tRecv: number; seq: number }[], sync: ClockSync): LinkStats;
```

**Clock sync** (NTP-style, over the reliable control channel)

1. The laptop sends `ping { t0 }`. The Phone replies `pong { t0, t1, t2 }` with its receive and send times. The laptop notes the arrival time `t3`.
2. For each sample, offset θ = ((t1 − t0) + (t2 − t3)) / 2 and round trip δ = (t3 − t0) − (t2 − t1).
3. Collect 20 samples, keep the quarter with the smallest δ, and use their median θ. Re-sync every 10 s and blend the new estimate in gradually to follow clock drift.
4. `toLocal(tPhone) = tPhone − θ`.

**Instruments**

- **Overlay** (toggle with `L`): one-way delay p50 and p95, packet loss from `seq` gaps, sample rate, current offset and round trip.
- **Flash test** (`latency.html?flash`, with `&input=phone` for the Phone): a large white flash the instant a Swing Onset is detected. Film the hand and the laptop screen together in slow motion, then count frames from the hand starting to move to the flash. Run it with each Input on the same laptop.
- **Detection test with the Phone** (`detection.html?input=phone`): the existing test, scoring Swings from the Phone Input instead of the Camera.

## P3-e Fallback and setup

**Goal**: make the Phone dependable for strangers. It still works when the network blocks peer-to-peer traffic, recovers when the Phone locks, can be picked from the start screen, and walks a new player through setup, including a safety prompt.

**Owns**: `src/phone/fallback.ts` and test, `src/phone/link.ts` (switching to relay), `server/signal.ts` (relay messages and rate limit), `src/render/inputPicker.ts`, `src/render/screens.ts` (the Input option on the start screen), `src/game/onboarding.ts` and test, `src/render/onboardingScreens.ts`, `src/game/timingOffsetStore.ts` and test, `src/main.ts` (wiring, the disconnect pause, haptics, deferred Zeroing).

**Depends on**: P3-c and P3-d (and P3-f for haptics on accepted Swings carrying a Face Angle).

**Behaviour**

1. **Relay fallback** (ADR 0004): if the motion channel isn't open 5 s after signaling starts, or it closes and doesn't reopen within 3 s, the Phone sends packets through the signaling WebSocket instead and the server forwards them to the laptop. Status becomes `relay`, and the latency overlay shows it. The server caps relay traffic at 120 messages per second per room and drops the excess, so a small free host isn't overwhelmed.
2. **Disconnect pause**: if the Phone locks or its page goes to the background, the game pauses the same way it does when the Camera loses the hand, with "Phone disconnected: unlock your phone". When the Phone page returns, it rejoins the same room automatically, re-syncs the clock, and play resumes with the existing Match countdown.
3. **Input picker**: Camera or Phone. The mouse stays a developer-only flag (`?input=mouse`) and is never offered to players.
4. **Setup steps with the Phone** (replacing the camera and framing steps):
   1. Safety prompt, first time only: grip firmly, use a wrist strap or a lanyard case if you have one, and clear space around you. The player taps "Got it"; remember it in `localStorage`, wrapped in try/catch.
   2. QR code, room code in large text, and connection status.
   3. Handedness, if not saved (the same setting as the Camera's).
   4. Zeroing.
   5. Timing calibration, if no Timing Offset is saved for the Phone.
   6. Continue, which unlocks once the Phone is connected and Zeroed.
5. **Timing Offset per Input**: store one Timing Offset per Input. An existing saved value becomes the Camera's.
6. **Haptics**: send `haptic { ms: 30 }` when a Swing is accepted as a Return or Serve. Send nothing on Early, Late or Miss.
7. **Zeroing during a Rally**: a `zero` that arrives mid-Rally is applied when the Rally ends.
