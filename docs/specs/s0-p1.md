# Spec: S0 foundation and P1 spin physics

Nov 19, 2026 · @Khiem · Rewritten after a design review against the repo, `GLOSSARY.md` and ADR 0001. This file is the source of truth; the Claude Docs copy is superseded.

## How to use this spec

This spec covers eight seams: one foundation seam (S0-a) and seven spin seams (P1-a to P1-d, P1-e1 to P1-e3). Each seam is one Claude Code session and one pull request. Start each session with:

```
Read docs/specs/s0-p1.md, CLAUDE.md and GLOSSARY.md. Implement seam <ID> only.
First propose a plan that lists every file you will create or change,
maps it to the seam's Owns list, and names the tests you will write.
Wait for my OK before writing code.
```

**Order**: S0-a → P1-a → P1-b and P1-c (parallel, separate git worktrees) → P1-d → P1-e1 → P1-e2 → P1-e3. Merge each seam before starting the ones after it.

## Project context

The game is **Return Drill**, a browser table tennis game: the **Feeder** at the far end sends **Feeds**, and the player returns them by swinging at a laptop webcam. MediaPipe Pose tracks the wrist; the game resolves each Swing from its timing and speed, never from Paddle–ball contact (ADR 0001). A target solver then computes the launch velocity that lands the ball where the game decided. Use the words in `GLOSSARY.md` in code, comments and tests: Feed (not serve), Feeder (not serve machine), Return (a successful one), **Shot** (any ball put into flight, Feed or attempted Return), Lift, Topspin, Backspin, Sidespin, Net-cord.

**Already built**: Vite + TypeScript + Three.js; Vitest with tests next to their modules (`*.test.ts`); MediaPipe Pose Landmarker with One Euro smoothing; a Swing detector (wrist speed in shoulder widths/s); the Feeder; a shot resolver with a Hit Window; a point-mass ball with gravity and drag, stepped at 240 Hz with swept table/net/floor collisions and the rally rules; a target solver with drag correction; mouse input (`?input=mouse`); a knob registry with a debug panel (`D`); tool pages (`latency.html`, `detection.html`); `npm run replay` for CSV frame logs.

**Invariants**

- Units: meters, seconds, radians per second. Spin knobs and readouts are in rev/s; convert at the edge (`revs * 2π`).
- Frame: origin on the floor under the table centre, y up, +z toward the player, net at z = 0, table top at y = 0.76 m.
- Clock: real time is `performance.now()` in ms; simulated seconds convert to it with `simSecondsToRealMs` and `TIME_SCALE`.
- Physics: fixed `PHYSICS_DT` = 1/240 s substeps from the accumulator in `simClock.ts`; never a variable timestep.
- Randomness: only through an injected `random: () => number` built by `makeRng(seed)`. No `Math.random()` or `Date.now()` in `src/game/` or `src/physics/`.
- Tuning guesses are knobs (`knobs.number(...)` in `constants.ts`), read with `.value` at the point of use. Pure functions take a params object; a `knob…Params()` helper builds it from the knobs (the `knobResolverParams()` pattern).
- ADR 0001: a Shot's outcome is decided by moving its target, never by adding noise to its launch. Spin follows the same rule.

## S0-a Spin types and seeded randomness

**Goal**: the shared vector and spin helpers every P1 seam needs, and deterministic randomness so physics and gameplay tests can pin exact outcomes.

**Owns**: `src/physics/vec3.ts`, `src/physics/spin.ts`, `src/util/rng.ts`, their tests; `src/game/ball.ts` (only to re-export `Vec3` from `src/physics/vec3.ts`); `src/game/feeder.ts` and `src/game/shotResolver.ts` (only to make `random` required instead of defaulting to `Math.random`) and their tests; `src/main.ts` (only to create the seeded `random` and pass it in); a new `src/game/noAmbientRandomness.test.ts`.

**Depends on**: nothing in this spec.

**Contract**

```ts
// src/physics/vec3.ts
export interface Vec3 { x: number; y: number; z: number }
export const ZERO: Readonly<Vec3>;
export function add(a: Vec3, b: Vec3): Vec3;
export function sub(a: Vec3, b: Vec3): Vec3;
export function scale(a: Vec3, s: number): Vec3;
export function cross(a: Vec3, b: Vec3): Vec3;
export function length(a: Vec3): number;

// src/physics/spin.ts
/** d = unit vector along the Shot's horizontal direction of travel. Spins in rad/s. */
export function spinVector(topspin: number, sidespin: number, d: Vec3): Vec3;
// = topspin * (ŷ × d) + sidespin * ŷ
export const revsToRadPerSec: (revs: number) => number;

// src/util/rng.ts
/** Uniform in [0, 1), deterministic for a given seed (e.g. mulberry32). */
export function makeRng(seed: number): () => number;
```

With the project frame, positive Topspin on a ball travelling toward −z gives a spin vector along −x, so the Magnus force (P1-a) points down.

**Implementation notes**

- `main.ts` takes the seed from `?seed=<n>` if present, otherwise from `crypto.getRandomValues`, and logs it to the console so a session can be reproduced.
- `noAmbientRandomness.test.ts` scans the source (not tests) under `src/game/` and `src/physics/` and fails on `Math.random` or `Date.now`.

## P1-a Magnus force and spin decay

**Goal**: give the ball spin that bends its flight: Topspin dips, Backspin floats, Sidespin curves; and let spin fade slowly.

**Owns**: `src/physics/flight.ts` and its test; `src/game/ball.ts` and `ball.test.ts`; `src/game/constants.ts` (new knobs `MAGNUS_K`, `SPIN_TAU_S` in the Physics group).

**Depends on**: S0-a.

**Contract**

```ts
// src/physics/flight.ts
export interface FlightParams {
  g: number;        // −9.81, along y
  k: number;        // drag constant, ≈ 0.14 /m
  kM: number;       // Magnus constant; knob MAGNUS_K, start 0.003
  spinTau: number;  // spin decay time constant, s; knob SPIN_TAU_S, start 4
}
/** a = g ŷ − k|v|v + kM (ω × v) */
export function flightAcceleration(velocity: Vec3, spin: Vec3, p: FlightParams): Vec3;
/** ω · e^(−dt/τ) */
export function decaySpin(spin: Vec3, dt: number, spinTau: number): Vec3;

// src/game/ball.ts (changes)
export interface BallState {
  readonly position: Readonly<Vec3>;
  readonly velocity: Readonly<Vec3>;
  readonly spin: Readonly<Vec3>;     // new, rad/s
  readonly seed: number;             // new: per-Shot seed (used by the Net-cord in P1-b)
  readonly status: BallStatus;
  readonly lastBounceHalf: TableHalf | null;
}
export function launchBall(position: Vec3, velocity: Vec3, spin?: Vec3, seed?: number): BallState; // defaults: zero spin, seed 0
export function stepBall(state: BallState, dt?: number, params?: FlightParams): { state: BallState; events: BallEvent[] };
export function knobFlightParams(): FlightParams;
```

`simulate` gains an optional `params` and passes it to `stepBall`; when omitted, both use `knobFlightParams()`.

**Physics** (semi-implicit Euler at `PHYSICS_DT`, as today): `v += a·dt` using `flightAcceleration`, then the existing swept move, then `spin = decaySpin(spin, dt, spinTau)`. Bounces and the net don't change spin in this seam (P1-b does). The floor never changes spin.

`kM` = 0.003 gives 7.5 m/s² of Magnus acceleration for 50 rev/s (314 rad/s) at 8 m/s, comparable to gravity. That's a game-feel guess, not a measured value, and the effect is strong: in the landing check below, 50 rev/s moves the landing about 0.7 m shorter (Topspin) or 1.6 m longer (Backspin) than no spin. P1-d tunes it.

**Done (Claude checks)**

- [ ] With zero spin, positions after 1 s match the old integrator to within 1 mm, for a Feed and a hard Return (capture golden values before changing code)
- [ ] Launch from (0, 1.0, 1.2) at 8 m/s toward −z, 10° up, measured where the centre first comes down to table-contact height: Topspin 50 rev/s lands at least 15 cm shorter than no spin, Backspin at least 15 cm longer
- [ ] Sidespin 20 rev/s on the same launch moves the landing sideways by at least 5 cm, in the direction ŷ × v gives
- [ ] `flightAcceleration` Magnus part is 7.4–7.7 m/s² for 314 rad/s at 8 m/s, spin perpendicular to velocity
- [ ] Terminal fall speed with no spin settles at 8.2–8.5 m/s
- [ ] Spin falls to e⁻¹ of its start after `spinTau` seconds (within 1%)
- [ ] `stepBall` does not mutate its input (frozen-object test)

**Out of scope**: bounce, net, solver changes.

## P1-b Spin-aware bounce and Net-cord

**Goal**: replace the flat friction factor at the table bounce with a contact model that trades speed and spin, so Topspin kicks forward and low and Backspin comes off no faster; and add a Net-cord.

**Owns**: `src/physics/bounce.ts`, `src/physics/net.ts`, their tests; `src/game/ball.ts` and `ball.test.ts` (the table and net branches of the sweep, and a new `cord` event); `src/game/constants.ts` (knob `TABLE_MU` replaces `BOUNCE_FRICTION`; new fixed constants for kappa and the cord).

**Depends on**: P1-a. Can run in parallel with P1-c.

**Contract**

```ts
// src/physics/bounce.ts
export interface BounceParams { e: number; mu: number; kappa: number; r: number } // 0.88, knob TABLE_MU 0.25, 1.5, 0.020
/** Ball touching a horizontal surface with normal +y and v.y < 0. Returns the outgoing velocity and spin. */
export function tableBounce(velocity: Vec3, spin: Vec3, p: BounceParams): { velocity: Vec3; spin: Vec3 };

// src/physics/net.ts
export type NetContact = 'clear' | 'cord' | 'dead';
/** Classify a crossing of z = 0 by the ball's bottom height (centre y − r). */
export function classifyNetCrossing(bottomY: number, netTopY: number, r: number): NetContact;
// bottom ≥ net top → clear; net top − r ≤ bottom < net top → cord; bottom < net top − r → dead
/** Velocity after a Net-cord. `random` is drawn from the Shot's own seed. */
export function cordVelocity(velocity: Vec3, random: () => number): Vec3;
```

**Bounce model** (µ = 0.25 and κ = 3/2 for a thin shell, from Sony AI's 2026 table tennis physics paper). Table normal `n` = +y; `u` is the contact-point slip velocity:

```latex
\mathbf{u} = \mathbf{v}_T - r\,(\boldsymbol{\omega} \times \mathbf{n}), \qquad \alpha = \min\!\left(\tfrac{2}{5},\ \frac{\mu(1+e)\,\lvert v_y \rvert}{\lvert \mathbf{u} \rvert}\right)
```

```latex
\mathbf{v}_T^{+} = \mathbf{v}_T - \alpha\,\mathbf{u}, \qquad v_y^{+} = -e\,v_y, \qquad \boldsymbol{\omega}^{+} = \boldsymbol{\omega} + \frac{\kappa\alpha}{r}\,(\mathbf{n} \times \mathbf{u})
```

`v_T` is the horizontal part of velocity. If `|u|` < 1e-9, skip the friction part. α = 2/5 = 1/(1+κ) is exactly the rolling limit. Using slip velocity (not the paper's tangential velocity) in α is a deliberate simplification.

A consequence to know: a ball that slides through the whole contact loses the same impulse µ(1+e)|v_y| whatever its spin, so Backspin only comes off slower than no spin when the no-spin ball would have reached rolling (steep, slow-sliding bounces). At 6 m/s, 30° down, both leave at 3.79 m/s; at 60° down, no spin leaves at 1.80 m/s and 50 rev/s Backspin at 0.56 m/s. Visible "check-up" in P1-d is therefore weak on shallow Feeds. That's the model, not a bug.

**Call sites in `ball.ts`**

- Table contact that is a bounce (`−v.y ≥ SETTLE_SPEED`): use `tableBounce` for velocity and spin. Table contact that is a settle (slower): keep today's behaviour (`v.y = 0`, horizontal speed × 0.9 as a fixed `TABLE_SETTLE_FRICTION`) so resting balls still stop; spin unchanged.
- Floor: unchanged (`bounceOffSurface` with the floor constants), spin unchanged.
- Net crossing (centre crosses z = 0 within the net's length): `classifyNetCrossing`.
  - `dead`: today's behaviour (status `dead`, `net` event, drop back with `NET_REBOUND`).
  - `cord`: status unchanged; emit a new `{ type: 'cord', position }` event; velocity from `cordVelocity`; lift the centre so the bottom sits on the net top, and don't classify the net again in the same substep.
  - `clear`: nothing.
- A Net-cord that then lands on the far half is a normal bounce for the rally rules (GLOSSARY: Net-cord).

**Net-cord rule** (game rule, tune for feel): vertical speed becomes `+|v_y| / 2` (upward); speed along z becomes `0.3 · v_z + nudge · sign(v_z)` with `nudge` uniform in ±`NET_CORD_NUDGE` (0.5 m/s, fixed), so the ball sometimes trickles over and sometimes drops back; x speed × 0.3. `random` is `makeRng(state.seed)` created at the contact, so the solver's and Feeder's look-ahead and the live ball cord identically.

**Done (Claude checks)**

- [ ] A ball dropped from 30 cm above the table with no spin rebounds to 22–24 cm
- [ ] A slipping ball whose α reaches 2/5 leaves rolling: `|u⁺|` < 1e-6
- [ ] Incoming 6 m/s toward −z, 30° down, 50 rev/s: Topspin leaves with more horizontal speed than no spin; Backspin leaves with no more horizontal speed than no spin (equal within 1e-9 here)
- [ ] Same at 60° down: Backspin leaves with strictly less horizontal speed than no spin
- [ ] Pure Sidespin (spin about y) leaves with the same horizontal velocity as the same ball with no spin
- [ ] `classifyNetCrossing` at the band edges: just below net top − r → `dead`; just above → `cord`; just below net top → `cord`; at net top → `clear`
- [ ] A cord leaves with upward vertical speed and emits one `cord` event; the same ball and seed give the same result twice; across 100 seeds some cords go over and some drop back
- [ ] A live ball that cords over and lands on the far half emits a `bounce` on that half and stays `live`
- [ ] `tableBounce` and `cordVelocity` don't mutate their inputs

**Out of scope**: Paddle contact (the game never simulates it, ADR 0001), the solver.

## P1-c Solver v2

**Goal**: one solver, used by the Feeder and the shot resolver, that turns a `ShotIntent` into a launch velocity and spin, accounting for drag and spin, and either guarantees net clearance and accuracy or reports failure.

**Owns**: `src/game/solver.ts` and `solver.test.ts`; the call sites in `src/game/feeder.ts` and `src/game/shotResolver.ts` and their tests; `src/game/constants.ts` (solver constants).

**Depends on**: P1-a. Can run in parallel with P1-b (the solver only needs flight up to the first landing).

**Contract**

```ts
export interface ShotIntent {
  target: TablePoint;   // landing spot on the table plane (may be off the table for a deliberate miss)
  flightTime: number;   // simulated s, launch to first landing
  topspin: number;      // rad/s, negative = Backspin
  sidespin: number;     // rad/s
}
export interface SolveOptions {
  netMargin: number;    // NET_CLEARANCE, 0.05 m
  maxPasses: number;    // 4
  maxRaises: number;    // 5
  bestEffort: boolean;  // false; true = return the last attempt instead of null
}
export interface ShotSolution { velocity: Vec3; spin: Vec3; flightTime: number; passes: number }
export function solveShot(from: Vec3, intent: ShotIntent, opts?: Partial<SolveOptions>): ShotSolution | null;
```

`solveLaunch` is removed; all callers and tests move to `solveShot`.

**Algorithm**

1. Spin: `spin = spinVector(intent.topspin, intent.sidespin, d)`, with `d` the unit horizontal direction from `from` to the target.
2. Start from the drag-free closed form, landing measured at table-contact height (`TABLE_TOP_Y + BALL_RADIUS`):

```latex
\mathbf{v}_0 = \frac{\mathbf{target} - \mathbf{p}_0 - \tfrac{1}{2}\mathbf{g}T^2}{T}
```

3. Refinement passes (up to `maxPasses`): simulate with the real `simulate` (same spin, seed 0) until the first landing (as `hasLanded` does today); correct `v.x`, `v.z` by landing error / T and `v.y` by the flight-time error. Stop when the miss is under 1 cm and the time error under 10 ms.
4. Net check: if the path crosses z = 0 less than `netMargin` above the net top (a cord or dead crossing counts as failing), multiply T by `ARC_RAISE_FACTOR` (1.1) and solve again, up to `maxRaises` times.
5. If it still misses by more than 2 cm or can't clear the net: return `null`, or the last attempt when `bestEffort`.

**Callers**

- **Feeder**: a `null` solve, or a Feed whose `findIdealTime` is `null`, is a failed draw: draw a new target (and in P1-e1, spin) with the same `random`, up to 5 times; then fall back to a zero-spin Feed at the centre of the target area. A Feed is never launched without an Ideal Time.
- **Shot resolver**: on `null`, retry the same target with zero spin; if that fails too, solve once more with `bestEffort: true` and launch it. A Return's planned outcome (including a deliberate long or wide miss) never changes because the solver failed; never move the target to "somewhere safe".
- Feeds and Returns launch with the solution's `spin` and a per-Shot `seed` drawn from `random` (`Math.floor(random() * 2 ** 32)`). In this seam every intent has zero spin.

**Done (Claude checks)**

- [ ] Golden test, captured before the change: for a fixed set of Feed and Return intents with zero spin, landing points match the old solver within 1 cm, and actual flight times are no further from the asked T than before
- [ ] Seeded property test, 1,000 intents in each direction (player → Feeder from 0.2–0.6 m above the table, and from 0.1 m below table height for late Returns; Feeder → player from `FEEDER_MOUTH`), targets anywhere on the far half at least 10 cm from the edges, T 0.5–1.2 s, Topspin −50 to +50 rev/s, Sidespin ±20 rev/s: every result is either `null` or lands within 2 cm of its target and clears the net by the margin
- [ ] At most 5% of those intents return `null`; mean passes ≤ 4
- [ ] Deliberate-miss targets (past the far end or side line): the result is `null` or passes table height within 2 cm of the target and never bounces on the table

**Done (you check)**: Return Drill plays as before; Feeds and Returns land where they used to.

**Out of scope**: choosing targets or spin (the Feeder's and resolver's job, P1-e1 to P1-e3), bounce physics.

## P1-e Spin in play (overview)

Spin reaches Return Drill in three seams, each one PR: **P1-e1** Feeds carry spin and the player can see it; **P1-e2** Lift puts Topspin on Returns; **P1-e3** a Feed's spin must be answered with the right Lift. ADR 0001 holds throughout: spin changes a Return only by moving its target.

**Out of scope for all three**: Backspin or Sidespin Returns, new Swing gestures, net misses from spin, Paddle contact.

## P1-e1 Spinning Feeds you can see

**Goal**: after each Streak speed-up, Feeds carry random Topspin or Backspin, and the player can see it on the ball.

**Owns**: `src/game/feeder.ts` and its test; `src/game/constants.ts` (knobs `FEED_SPIN_STEP_REVS`, `FEED_SPIN_MAX_REVS`, `SPIN_DRAW_MAX_REVS`); `src/render/scene.ts`, `src/render/drawnBall.ts` (spinning stripe); `src/main.ts` (only to pass the ball's spin to `syncBall`).

**Depends on**: P1-d merged (so spin ranges are picked with tuned physics).

**Feed spin**

- Each Feed draws its Topspin uniformly from ±`min(speedUps × FEED_SPIN_STEP_REVS, FEED_SPIN_MAX_REVS)`, where `speedUps` is the existing `floor(streak / FEED_SPEEDUP_EVERY)`. So the first Feeds have no spin, and spin arrives with the speed-ups. Negative is Backspin. No Sidespin.
- A failed draw (P1-c) redraws spin along with the target.

**Seeing spin**

- Draw a stripe (or logo band) on the ball that rotates about the true spin axis. The drawn rate is monotonic in the real rate and capped: `SPIN_DRAW_MAX_REVS × tanh(|ω| / (2π · 30))` rev/s. Real rates (20–80 rev/s) would alias at 60 FPS.
- `syncBall` takes the spin as well as the position.

**New knobs** (starting guesses)

| Knob | Group | Range | Default |

## P1-e2 Lift puts Topspin on Returns

**Owns**: `src/game/shotResolver.ts` and its test; `src/game/constants.ts` (knobs `LIFT_FULL`, `RETURN_TOPSPIN_MAX_REVS`).

**Depends on**: P1-e1 (the stripe makes Return spin visible).

**Return spin**

## P1-e3 Answering a Feed's spin

**Goal**: the player must answer a Feed's spin with the right Lift, or the Return lands short (Backspin) or long (Topspin).

**Owns**: `src/game/shotResolver.ts` and its test; `src/game/constants.ts` (knob `SPIN_ANSWER_M`, constant `RETURN_MIN_DEPTH_M`).

**Depends on**: P1-e2.

**Answering spin** (ADR 0001: only the target moves)

Let `s` = Feed Topspin / `FEED_SPIN_MAX_REVS`, clamped to [−1, 1].

- Against Backspin (`s < 0`): the Return's depth past the net shrinks by `SPIN_ANSWER_M × max(0, −s − Lift)`, clamped so it never lands closer than `RETURN_MIN_DEPTH_M` (0.2 m, fixed) past the net. Too little Lift against Backspin lands short, never in the net.
- Against Topspin (`s > 0`): depth grows by `SPIN_ANSWER_M × max(0, Lift − (1 − s))`. Too much Lift against Topspin goes long, and can go off the end: a real miss, like today's long push.
- No spin: no change, so zero-spin play is exactly as before.
- This adds to the existing depth (power, timing risk, scatter); it does not replace it.

**New knob**: `SPIN_ANSWER_M`, group Return, 0–1 m, default 0.3 (starting guess).
